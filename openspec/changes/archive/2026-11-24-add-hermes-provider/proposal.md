## Why

Paseo 0.17.4 bundles a new plugin provider, `hermes` (`dist/server/builtin-plugins/hermes-provider/server/provider.ts`: `id: "hermes"`, label "Hermes", "Nous Research self-improving AI agent", `command: ["hermes", "acp"]`, `requiresConfiguration: true`; the plugin requires Paseo >= 0.17.3). Before 0.17.4 Hermes was only a catalog entry users could add as a generic ACP provider; 0.17.4 migrates such hand-written `extends: "acp"` entries to the bundled plugin, as it did for goose. The `providers` option must list exactly the pinned Paseo's providers minus the excluded ones, so with the 0.17.4 pin `check-providers.sh` fails until the add-on either offers Hermes or excludes it:

```
Paseo 0.17.4 plugin providers:      antigravity fx goose hermes hoplite muse
add-on schema providers:            antigravity claude codex copilot fx goose muse omp opencode pi
ERROR: the providers option in paseo/config.yaml does not match Paseo 0.17.4's providers
```

Hermes can run inside the add-on, so it is supported like fx, goose, Muse Code and Antigravity rather than excluded like Hoplite:

- It is open source (MIT, `NousResearch/hermes-agent`), not a sponsored or paid service. It sends model requests to the model provider the user configures (OpenRouter, Nous Portal, OpenAI, Anthropic, ...).
- It is not published to npm. Its documented installer (`curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash`, byte-identical to `scripts/install.sh` in the repo) clones the latest stable release into `--dir`, then bootstraps a pinned uv and Python and hands over to Hermes' own package manager, which installs hash-verified Python dependencies, Node.js, pnpm and ripgrep into a tool store under `$HERMES_HOME` (`~/.hermes`), builds the terminal and web UIs, and publishes the `hermes` command in the checkout's `.hermes/bin`. It explicitly supports musl: it detects a musl userland and picks the `*-linux-musl` uv, Python, Node.js, pnpm and ripgrep builds (both x86_64 and aarch64 are in `pm/lock.json`), and on musl only requires the system `libstdc++`, which the add-on image already has. `--non-interactive` skips its setup and gateway prompts; `--skip-browser` and `--skip-computer-use` leave out Chromium and cua-driver, which have no musl builds (`pm/lock.json` lists only glibc targets for them) and nothing to drive in a headless add-on.
- Checked in the add-on image (Paseo 0.17.4, Alpine, x86_64). The Home Assistant base image sets `UV_EXTRA_INDEX_URL` and `PIP_EXTRA_INDEX_URL` to HA's musllinux wheel index. With them set the installer fails in its dependency sync (`wheel` is found on that index, but not at the locked `wheel==0.48.0`, and uv only uses the first index that has a package), so the hook runs the installer with both unset (`env -u`). Then the real installer installs Hermes v0.23.4 in about 110 s (~1.1 GB checkout with its `.git`, `node_modules` and venv; ~1 GB tool store and caches in `~/.hermes`); `hermes --version` prints `Hermes Agent v0.23.4 (2026.9.24) · stable · local 8fc037444731` on its first line; `hermes acp` answers an ACP `initialize` (agent `hermes-agent` 0.23.4, auth method `hermes-setup`). `hermes update` from v0.23.3 to v0.23.4 succeeds with the HA index variables still set (its package manager isolates its own syncs), so only the bootstrap needs them removed.
- aarch64 could not be run on this host (no emulation). `uv.lock` was checked instead: every compiled dependency the x86_64 install pulled in also has a `musllinux` aarch64 wheel, and the dependencies without any musl wheel (torch, onnxruntime, playwright, ...) belong to optional extras the installer does not install on musl, as the x86_64 install shows.
- The launcher binds the Python of the tool store in `~/.hermes/tools` and the checkout path, so both have to stay where the installer put them. The checkout goes into the provider's own directory (`/data/agents/bin/hermes/hermes-agent`; the installer stages its clone next to `--dir`, so a subdirectory keeps a killed install's staging inside the provider directory, which the hook empties before every install). The command lives in `hermes-agent/.hermes/bin`, so the hook learns that a script provider's CLI can sit in a subdirectory of its provider directory (`PROVIDER_CLI_SUBDIR`): the version check, the binary lookup and the daemon PATH use that directory; emptying and removal still use the whole provider directory. The tool store, Hermes' settings (`config.yaml`, `.env`), sessions and caches stay in `/data/home/.hermes` like every other agent's home data, so deselecting keeps them (about 1 GB), which DOCS.md says and tells users how to free.
- The first install takes far longer than the other CLIs (a git clone, ~1 GB of downloads, two UI builds): ~2 minutes on a fast x86_64 host, more on slow hosts or links. The default 600 s cap could make a slow host fail and redo the whole download on every start, so a script provider may carry its own cap (`SCRIPT_TIMEOUT`; Hermes 1800 s). `PASEO_HA_PROVIDER_INSTALL_TIMEOUT`, when set, still caps every install (the providers test uses it).
- Hermes does not update on its own: `hermes --version` reports "Up to date" or an available update, and `hermes update` moves the checkout to the next stable release. Like Muse Code, Antigravity and fx, the hook does not update it; DOCS.md tells users to run `hermes update`, and the next start records the new version.
- Paseo registers Hermes with `requiresConfiguration: true` (like fx and goose): it only registers the provider once `agents.providers.hermes` exists. With `hermes` in `ALL_PROVIDERS` the hook always writes that override, enabled when Hermes is selected and its CLI runs, disabled otherwise.
- **Hermes needs a running gateway, and cannot start one itself in the add-on.** With Hermes installed and enabled, Paseo listed it as `error` ("Failed to refresh provider snapshot"), and a direct ACP `session/new` failed with `Gateway inaccessible: service_identity_unverified (cannot read the container's HERMES_HOME: ... '/run/s6/container_environment/HERMES_HOME')`. Hermes' clients (`hermes acp`, the TUI) attach to a gateway runtime; when none runs, `ensure_gateway_runtime` asks the host's service manager, and `hermes_cli/service_manager.py::_s6_running()` treats any container whose PID 1 is `s6-svscan` (every Home Assistant add-on) as Hermes' own Docker image: it then requires a registered `gateway-<profile>` s6 service whose run script uses `/opt/data` and a `hermes` user (`S6ServiceManager._render_run_script`). Nothing about that can be satisfied from outside without imitating Hermes' private image layout. A gateway that is already running is found first, though, and Hermes documents how a foreign supervisor runs one: `hermes gateway run --no-supervise` stays in the foreground instead of redirecting to s6, and `--external-supervisor` makes `hermes update` hand the gateway back to its supervisor (it exits with 75) instead of relaunching it itself. So the add-on gets an s6 longrun, `hermes-gateway`, that runs `hermes gateway run --no-supervise --external-supervisor --replace -q` while the `hermes` CLI is on the daemon's PATH (selected and installed) and otherwise exits and is not restarted (finish exit 125); exit 75 restarts it on the updated code, a fatal configuration exit (78) stops it until the next start, other exits restart it after a short pause. Its logs stay in `~/.hermes/logs` (`-q`, stdout discarded). Proven in the built image: with the service, Paseo lists Hermes `available` with its modes (Default, Accept Edits, Don't Ask, Full access); `paseo run --provider hermes` against a local OpenAI-compatible mock completes and answers `PONG`; without a model provider Hermes answers "not connected to any AI provider yet" through Paseo; `hermes update` from v0.23.3 (with the HA index variables set, as in a Paseo terminal) updates to v0.23.4, hands the gateway back (exit 75), the service restarts it on the new code, and the next Paseo turn completes; with `providers: [pi]` the service stays down and is not restarted. The gateway uses about 215-265 MB of memory while Hermes is selected (DOCS.md says so).
- The installer also writes `~/.local/bin/hermes` wrappers and appends a `~/.local/bin` PATH line to `~/.bashrc` and `~/.profile` in `/data/home`. DOCS.md already says vendor installers may add PATH lines and that the add-on sets `PATH` itself.

## What Changes

- `paseo/rootfs/etc/paseo-ha/init.d/20-providers.sh`: add `hermes` to `ALL_PROVIDERS` as a script provider: binary `hermes`, provider directory `/data/agents/bin/hermes`, CLI directory `hermes-agent/.hermes/bin` inside it (new `PROVIDER_CLI_SUBDIR` map and `provider_cli_dir`, used for the binary lookup, the `--version` PATH and the daemon PATH), installer `https://hermes-agent.nousresearch.com/install.sh` run with `bash`, `--dir /data/agents/bin/hermes/hermes-agent --non-interactive --skip-browser --skip-computer-use`, and `env -u UV_EXTRA_INDEX_URL -u PIP_EXTRA_INDEX_URL`. New `SCRIPT_TIMEOUT` map (Hermes 1800 s) used unless `PASEO_HA_PROVIDER_INSTALL_TIMEOUT` is set. Header comments: eleven providers, Hermes is not on npm, configuration-required providers include Hermes.
- New s6 longrun `paseo/rootfs/etc/s6-overlay/s6-rc.d/hermes-gateway` (`type`, `run`, `finish`, dependency on `init-paseo`, listed in `user/contents.d`): runs Hermes' gateway as described above while `hermes` is selected and installed; no process and no restarts otherwise.
- `paseo/config.yaml`: `hermes` added to the `providers` enum and to the add-on description; default stays `[pi]`.
- `paseo/translations/en.yaml`: the `providers` description names Hermes, its ~2 GB download with its own runtime and `hermes update`.
- `paseo/DOCS.md`: intro, options row, "Agent providers" (five bundled plugin providers; Hermes is configured by the add-on), provider table row, a "Which versions are installed" bullet (where Hermes and its runtime live, size, install time and cap, no browser/computer-use tools, `hermes update`, what deselection keeps), login steps (`hermes setup`), first-start note, troubleshooting rows, known limitations (no HA setup for Hermes; Hermes adds ~2 GB to `/data` backups).
- `paseo/tests/smoke/run.sh`: new check g): with the smoke options (`providers: [pi]`) the `hermes-gateway` service is down and not wanted up, and no Hermes gateway start is logged.
- `paseo/tests/providers/run.sh`: the stub installer handles Hermes (`--dir`, refuses a non-empty directory, requires `--non-interactive`, `--skip-browser` and `--skip-computer-use`, refuses to run while `UV_EXTRA_INDEX_URL`/`PIP_EXTRA_INDEX_URL` are set, installs `hermes` into `.hermes/bin` and prints Hermes' multi-line version); every "all providers" assertion includes `hermes`; new checks: the image sets the HA index variables, Hermes installed into its checkout, stamped and named in the `Providers:` line with the first line of its version, its CLI directory on the daemon PATH, removed with its whole directory on deselection while `/data/home/.hermes` is kept, and the install time cap (the variable overrides a provider's own cap; a slower installer within the cap completes).
- `.github/scripts/check-providers.sh`: comment only (Hermes is a bundled plugin provider from 0.17.4); the check passes for 0.17.4 and still fails for 0.17.3.
- `paseo/README.md` and the root `README.md` list Hermes (eleven agents), say Hermes is updated with `hermes update`, and include Hermes among the agents without the bundled HA skill and MCP tools. `SECURITY.md` and the bug report template's provider list name Hermes (exempt from Rule 1, updated for consistency).
- Spec delta for `agent-providers`: "Provider selection option" names `hermes` and lists it with fx and goose as registered through the per-provider override; "Paseo providers follow the selection" lists Hermes among the disabled providers; "Vendor-installed providers" covers a CLI in a subdirectory of its provider directory, an installer environment the base image would break, a per-provider install time cap, and Hermes' install and update. ADDED requirement "Hermes gateway runtime": the add-on runs and supervises Hermes' gateway while Hermes is selected and installed, restarts it on the updated code after `hermes update`, and runs nothing for it otherwise.

None.

## Impact

- `paseo/rootfs/etc/paseo-ha/init.d/20-providers.sh`, `paseo/rootfs/etc/s6-overlay/s6-rc.d/hermes-gateway/*`, `paseo/rootfs/etc/s6-overlay/s6-rc.d/user/contents.d/hermes-gateway` and `paseo/config.yaml` (shipped; released with the version bump of the `bump-paseo-0-17-4` change in the same PR).
- `paseo/translations/en.yaml`, `paseo/DOCS.md`, `paseo/README.md`, `paseo/tests/providers/run.sh`, `paseo/tests/smoke/run.sh`, `.github/scripts/check-providers.sh` (not shipped), plus the exempt repo docs above.
- Users who select `hermes` get a ~2 GB download (checkout in `/data/agents/bin/hermes`, runtime in `/data/home/.hermes`) on the next start, which takes a few minutes, and choose a model provider with `hermes setup` or `hermes model` in a Paseo terminal, or set that provider's API key in `env_vars`. While Hermes is selected its gateway runs in the add-on (about 250 MB of memory). Users who do not select it see no change (nothing is downloaded; Paseo lists Hermes as disabled). The other script providers are unchanged (their CLI directory is their provider directory, and their install cap stays 600 s).
